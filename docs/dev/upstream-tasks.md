# Tasks from the original club app

Kabine started as the app of one handball club, which is still developed on its own. New features and bug fixes made there are listed here so they can be brought into Kabine. Whoever works on Kabine takes an open entry, ports it the Kabine way (English source, Lingui, club profile instead of club data, modules, tests) and moves it to "Done" with the Kabine commit.

Entries describe the change, not the club: no names, domains or data of the club.

Format per entry: date, title, what changed and why, where in the code (file and function names are the same in both code bases unless noted), and anything that needs adapting for Kabine.

## Open

- **2026-11-10 Audit log for admins (follows from the trust model entry below).** Instead of restricting trusted coaches further, the club app makes actions with large effect traceable: Admin → "Protocol" lists who did what to whom and when. Logged: account removed, personal link (with "previous devices signed out"), club exit, person deleted, admin rights granted or removed, member added or removed (incl. stand-ins and coaches), set inactive and active again, guardianship removed or set by an admin, schedule source linked or removed, schedule sync with new, moved or cancelled games, event cancelled or un-cancelled, special event deleted, team deleted, season change, export. Not logged: everyday things (responses, squad, chat, helper duties). Table `audit_log` (migration `0030_audit_log.sql` in the club app): time, actor person id and name, action, person id and name, team id and name, event id, short detail (≤ 300 chars); names as a snapshot so entries about deleted people stay readable, and on deletions the entry is written in the same batch before the delete. `worker/domain/audit.ts` (`audit`, `auditStmt`; a failed entry never blocks the action), `GET /admin/audit-log?before=<id>` (admins only, 100 per page), `src/pages/audit.tsx` grouped by day, labels in `AUDIT_LABELS` (shared). Data minimisation: admins only, no new personal fields, emptied by the season change (then only the season change itself is in it), not in the export. Tests: `test/audit.test.ts`, the season-change test, e2e "Protokoll". In Kabine: texts through Lingui, modules (duties, referees) can add their own actions via a hook, and `docs/privacy.md` needs a line about it.

- **2026-11-10 Security audit of the club app: three bugs Kabine has too.** A full audit of the original app (outside access, and actions beyond one's own rights) found these; the same code is in Kabine. Port each with its test and add it as a rule to `docs/dev/security.md`.
  1. *E-mail code can be guessed in parallel.* `checkEmailCode` reads `attempts`, compares, and only then increments; concurrent requests all read the same count. In the club app's test 15 of 200 parallel guesses were evaluated instead of 5, in production likely more. The per-address send limit lives in KV (read, then write), so it is not atomic either. Fix in the club app (`worker/domain/email-login.ts`): book the attempt first in one statement, `UPDATE email_codes SET attempts = attempts + 1 WHERE id = ? AND attempts < 5 AND used_at IS NULL`, compare only if a row changed, give the attempt back on a correct code (the account chooser verifies twice); compare hashes with `safeEqual`. Enforce the per-address limit in the same `INSERT … SELECT … WHERE (SELECT count(*) …) < limit` that creates the code (5 per hour, plus a new cap of 10 per day, which bounds guessing a 6-digit code to 50 tries per address and day); the per-IP limit stays in KV as an extra brake. Same for the SMS channel. Tests: "gleichzeitige Fehlversuche …" and "höchstens fünf Codes pro Adresse und Stunde und zehn pro Tag …" in `test/email.test.ts`.
  2. *Chat role label can be forged.* `GET /chat/:teamId/connect` copies all client headers (`new Headers(c.req.raw.headers)`) and only overwrites `x-label` when the server assigns one. Players get none, so a custom client sending `x-label: Coach` appears as "Coach" to everyone, in chats with children. Fix: a helper `upgradeHeaders(request)` in `worker/lib/http.ts` that copies only `upgrade`, `connection` and `sec-websocket-*`; build the DO request from it plus the server's own headers. Use it for the duty hub connects too (`modules/duties/worker/routes.ts`, `modules/youth-referees/worker/plan-routes.ts`), which also pass raw client headers. Test: "ein mitgeschicktes Etikett des Clients wird nicht übernommen" in `test/chat.test.ts`.
  3. *Chat rights are checked only at connect.* An open socket keeps reading and writing after the person is removed from the team, leaves the club, a parent switches off "read chat", the guardianship is removed, the account is removed or a device is signed out, an admin loses admin rights; a new coach role only applies after reconnecting. Fix: a DO endpoint `/kick { personIds | all }` that closes matching sockets with code 4004, and `revalidateChatAccess(env, { personIds, teamIds?, withGuardians? })` plus `reconnectChats(env, teamIds)` in `worker/domain/chat.ts`, called at every place that changes chat access (team member removed or added, leave, child permission for chat, guardianship removed, account removed, device signed out from the device list, personal link that revokes old devices, admin flag removed, person deleted; all rooms after the season change and after changing age-class child limits). Not on one's own logout: other devices would visibly reconnect for a second. The app on 4004 reloads the room list and reconnects, so it gets the current rights or none (`src/pages/chat.tsx`). Tests: "aus der Mannschaft entfernt …" and "Eltern schalten „Chat lesen“ ab …" in `test/chat.test.ts`.

  Already covered in Kabine (rules 1, 2, 4, 5, 7 in `docs/dev/security.md`), no port needed: WebSocket origin check, read-only views not moderating, staff access managed by admins, schedule import across teams, shared training rules. The owner protection in Kabine uses the recorded owner person, so the club app's issue (an unverified e-mail address on any account counted as the owner's) does not apply.

- **2026-11-10 Document the trust model of a club (wanted by the maintainer).** The audit raised the question how far the app should guard against coaches. The answer of the original club: a club rests on trust, especially in its coaches, and the app should reflect that. Please document it in `docs/dev/security.md` (threat model, which today says most damage would come from a logged-in coach) and in the club docs (`docs/` operation and privacy, German too), roughly:
  - Coaches are trusted with their teams; admins with the club. The app does not build general distrust of coaches into everyday flows (adding stand-ins, managing them, shared trainings stay simple).
  - What is closed anyway: anything a person without login or any logged-in user (often a child) could exploit; anything a hijacked account could use to take over another person's access or to reach far beyond the hijacked role; and anything that happens easily by accident with large effect (wrong schedule link, club-wide actions that cannot be undone).
  - Highest priority for every security change: people using the app in good faith notice no difference. Check production data for who a new rule would hit before shipping (the club app found three coaches without an account who joined through their team's player link; the rule that would have blocked them was dropped).
  - Prefer a narrow guard on the risky step plus clear wording ("please agree with the coach of …", "an admin enters this") over removing a feature.
  - Club-specific choices, not Kabine defaults: in the club app only admins enter a club exit (coaches set people inactive or remove them from their team), and the same handball4all schedule can be linked to one team only ("team X already uses this schedule, please agree with its coach"); Kabine's stricter import rule 1 stays.

- **2026-11-09 Briefing: qualifications instead of a youth referee role (core redesign, wanted by the maintainer).** Kabine has two separate mechanisms for "only suitable people may take this duty": duty types with `needs_skill`, which a person switches on themselves in the profile ("What I can do", `skill_consents` per account), and the youth referee role (`referees`, `referee_links`, module `youth-referees`) that admins grant. A club in the original app added a duty type "Tournament management" that should only be taken by people an admin has approved; neither mechanism fits (self-consent is too loose, a role per duty type is too much). Goal: one general **qualification** model in the core; youth referees become a preconfigured qualification of the handball sport profile, and the module disappears. Other sports get referees, scorers or licensed timekeepers without their own module.

  *Model.* Every duty type that needs prior knowledge says who grants it: `grant = 'self'` (as today: the person consents in the profile) or `grant = 'admin'` (only admins grant it). Store admin grants per **person**, not per account, because children without an account can be qualified and parents act for them: e.g. `qualifications (person_id, duty_type_id, granted_by, granted_at, PRIMARY KEY (person_id, duty_type_id))`, FKs with `ON DELETE CASCADE`. Self-consents may stay per account (`skill_consents`) or move to the same table with `granted_by = person_id`; decide and migrate once. `mayTake` checks consent for `self` types and a grant for the person who will do the duty (the person themselves, or the child for "Who referees?") for `admin` types. Coaches and admins entering others keep ignoring prior knowledge (existing rule).

  *What the youth referee role does today, generalised per qualification:*
  1. **Required duty per age class.** Home games of age classes with `youth_referee` get the referee duty automatically, also without a helper plan or template. Generalise to "required duty types per age class" (age class setting or sport profile), with the youth referee duty as the handball default for the youngest classes.
  2. **List per qualification.** Referees have their own view of the helper plan across all teams (all open referee slots of all games). Generalise: everyone with an `admin` qualification gets a chip/view "<qualification>" in the helper tab with the open slots of that duty type across teams (today `GET /duties/referee`, `REFEREE_TEAM_SQL`, live hub with key 0).
  3. **Children do it themselves.** A qualification can belong to a child; the parent sees it and can sign the child up ("Who referees?"), the child signs up itself if it has an account. Keep the child-permission and age-class child-limit rules.
  4. **Automatic group.** `teams.auto_members = 'referees'` becomes "members are everyone with qualification X" (e.g. `auto_members = 'qualification:<dutyTypeId>'` or a separate column). Leads are managed by hand (see the entry of the same day: admins are no longer added automatically).
  5. **Grant by link.** `referee_links` becomes a link per qualification ("Grant tournament management"), hashed, single or multi use as today; plus switches in the person sheet under "Roles in the club" for every `admin` qualification.
  6. **Notifications.** "Youth referee wanted" (`duty_referee_open`) becomes "<duty type> wanted" for the qualified people; the existing "open slots" logic must respect grants, not only consents (club app: `worker/domain/duty-notify.ts` reads `skill_consents`).

  *Admin UI.* Duty type sheet: "Needs prior knowledge" → choice "Who approves: the person in the profile / an admin". Person sheet: under "Roles in the club" one switch per admin qualification. Profile "What I can do": self qualifications as switches, admin qualifications only as information ("Approved by an admin") when granted.

  *Migration for existing clubs.* `referees` rows → grants of the youth referee duty type (`grant = 'admin'`), `referee_links` → links of that qualification, the auto group switches to the new member rule, `who_referees` on duty types becomes "qualified people"; keep the previous release working (add now, drop the old tables in a later release) and write the upgrade test. Privacy: a qualification is personal data (visible to admins, the person, their parents and coaches when entering duties); add it to `docs/privacy.md` and the export.

  *Club app status.* The original app does the small step now (2026-11-09): duty types with prior knowledge get "approved by an admin", grants per person in a new table, switches in the person sheet, profile shows them read-only, `mayTake` and the open-slot notifications check them; the youth referee role stays as it is there until Kabine has this redesign. A separate entry will describe that change once it is live.
