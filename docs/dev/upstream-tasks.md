# Tasks from the original club app

Kabine started as the app of one handball club, which is still developed on its own. New features and bug fixes made there are listed here so they can be brought into Kabine. Whoever works on Kabine takes an open entry, ports it the Kabine way (English source, Lingui, club profile instead of club data, modules, tests) and moves it to "Done" with the Kabine commit.

Entries describe the change, not the club: no names, domains or data of the club.

Format per entry: date, title, what changed and why, where in the code (file and function names are the same in both code bases unless noted), and anything that needs adapting for Kabine.

## Open

- **2026-11-09 Team setting "Whole team at games".** Wanted by a youth coach: all players come to every game (and help, ride along), but only some play. New per-team switch (teams only, not groups), default off: migration `0028_game_all_players.sql` adds `teams.game_all_players INTEGER NOT NULL DEFAULT 0 CHECK (game_all_players IN (0, 1))`. When on, every active player of the team is a participant of its games with status "yes" by default and declines if they cannot come; the squad nomination only decides who plays. `Participant` gets `nominated: boolean` (`worker/domain/events.ts`: nominated players as before, then all players of event teams with the switch who are not nominated, with `nominated: false`); `toSummary` shows counts without a published squad when `game.allPlayers`, adds `game.allPlayers` and `game.nominatedCount`; `toDetail` participants carry `nominated`. Pills (`SquadPill` in `src/ui.tsx`): "Squad follows" before publication, then "Not nominated" / "Nominated"; on the event page the coach's "yes" chips mark nominated players darker with a legend; the squad page shows declines of non-nominated players (`squad.tsx`). Carpools are open to all participants immediately (`mayViewCarpool` in `worker/domain/carpool.ts`). Notifications stay with the nominated only, to avoid notification fatigue: game reminders (`sendGameReminders` in `worker/cron.ts`), the late-decline push to coaches and the new-event push (`worker/routes/events.ts`). API: `gameAllPlayers` in `GET /teams/:id` and `PATCH /teams/:id` (refused for groups). The club app announced it with a coach-only message of the day. Tests: `test/game-all-players.test.ts`, e2e "Whole team at games". A club-wide default may follow later; in Kabine consider it as a club profile default for new teams.

- **2026-11-09 Info buttons instead of explanation texts next to settings.** The app has many switches, and the explanation lines under them got long. Now an "i" button next to a switch or a section heading opens a sheet with a plain-language explanation, optionally an example, and "Got it". All texts live in one place, `src/help-texts.ts` (`HELP` record: title, text, optional example; `HelpTopic` type), one entry per setting; new switches on settings pages get their entry there. Components in `src/ui.tsx`: `InfoButton({ topic })` (`icon-btn info-btn`, aria-label "Explanation: <title>") and `SwitchRow({ info, ...switchProps })`, which wraps the switch and the button (`.switch-with-info`, `.section-title .info-btn` in `styles.css`). Rule: a switch or heading with an info button has no sub text and no explanation paragraph any more (both together was redundant); hints that depend on state (e.g. whether a child already has an account) and sub texts of switches without an info button stay. Covered: team settings (decline deadlines, automatic squad, whole team at games, responses visible, helper plan), groups (responses visible, involve parents), admin (involve parents, children in the app, prior knowledge, roles in the club, admin approvals, schedule sync reminder), profile (admin mode, calendar feed, permissions for my child). In Kabine every text goes through Lingui; modules should be able to register their own help topics (hook in `src/module-api.ts`). E2E checks the button on the "whole team" switch.

- **2026-11-09 Duty types approved by an admin are hidden from people without the approval.** Follow-up to the entry "Duty types whose prior knowledge an admin approves" below: people without the approval saw the duty with "Only with approval"; the club wanted them not to see it at all. In the helper tab list (`teamDutyGames` in `worker/routes/duties.ts`) a block of a `needs_skill` + `skill_grant = 'admin'` type is only returned to people with the grant, to managers of the event (coaches, admins, organisers, so they can still enter anyone), and to whoever already has an entry in it (own or for their child, e.g. after the grant was revoked); "Only with approval" now only shows in those cases. Event page, home chips and "helpers wanted" notifications already ignored such slots for people without the grant. Help texts adjusted. Test in `test/duties.test.ts`.

- **2026-11-09 Delete a duty type, only when it is used nowhere.** Admins could only archive duty types. Now the duty type sheet has "Delete duty type": allowed only if the type is in no template and in no time block of any event, past ones included (those rows would cascade away with the helpers' entries); otherwise the button is disabled with "cannot be deleted while it is in N time blocks / N templates, archiving hides it for new things" and the server answers 409 `duty_type_in_use` with the same advice. Own consents and admin grants are not "use" and are deleted with it. The youth referee type can never be deleted (409 `referee_type`). `GET /duty-types` returns `usage: { blocks, templates }` for admins only. Club app: `dutyTypeUsage` and `DELETE /admin/duty-types/:id` in `worker/routes/duties.ts`, `DeleteDutyType` in `src/pages/duty-admin.tsx`, tests in `test/duties.test.ts` and e2e. In Kabine the duty types live in the duties module.

- **2026-11-09 Duty types whose prior knowledge an admin approves (small step of the qualifications briefing).** Live in the club app. Duty types with `needs_skill` get `skill_grant` (`'self'` as before, or `'admin'`); admin approvals are stored per person in `skill_grants (person_id, duty_type_id, granted_by, granted_at)`. `loadSkills(db, accountId, personId)` returns consents and grants, `mayTake(type, skills)` checks the grant for `admin` types (earlier self-consents no longer count after switching a type to `admin`); block view gets `skillByAdmin`, the helper tab shows "Only with approval" instead of the profile link; signup error explains it. Admin UI: duty type sheet "Who approves: the person / an admin"; person sheet under "Roles in the club" one switch per admin type (`PUT/DELETE /admin/skill-grants/:personId/:dutyTypeId`, `skillGrants` in `GET /admin/persons`); profile "What I can do" lists granted ones as information only. Open-slot notifications (`duty-notify.ts`) check grants per person. Export in Kabine format omits `skill_grant` and `skill_grants` until Kabine has them. Club app files: migration `0027_skill_grants.sql`, `worker/domain/duties.ts`, `worker/routes/duties.ts`, `worker/routes/referees.ts`, `worker/routes/persons.ts`, `worker/domain/duty-notify.ts`, `src/pages/duty-admin.tsx`, `src/pages/admin.tsx`, `src/pages/profile.tsx`, `src/pages/helpers.tsx`; tests in `test/duties.test.ts` and e2e. For Kabine this is the starting point of the qualification redesign described in the briefing entry of the same day.

- **2026-11-09 Briefing: qualifications instead of a youth referee role (core redesign, wanted by the maintainer).** Kabine has two separate mechanisms for "only suitable people may take this duty": duty types with `needs_skill`, which a person switches on themselves in the profile ("What I can do", `skill_consents` per account), and the youth referee role (`referees`, `referee_links`, module `youth-referees`) that admins grant. A club in the original app added a duty type "Tournament management" that should only be taken by people an admin has approved; neither mechanism fits (self-consent is too loose, a role per duty type is too much). Goal: one general **qualification** model in the core; youth referees become a preconfigured qualification of the handball sport profile, and the module disappears. Other sports get referees, scorers or licensed timekeepers without their own module.

  *Model.* Every duty type that needs prior knowledge says who grants it: `grant = 'self'` (as today: the person consents in the profile) or `grant = 'admin'` (only admins grant it). Store admin grants per **person**, not per account, because children without an account can be qualified and parents act for them: e.g. `qualifications (person_id, duty_type_id, granted_by, granted_at, PRIMARY KEY (person_id, duty_type_id))`, FKs with `ON DELETE CASCADE`. Self-consents may stay per account (`skill_consents`) or move to the same table with `granted_by = person_id`; decide and migrate once. `mayTake` checks consent for `self` types and a grant for the person who will do the duty (the person themselves, or the child for "Who referees?") for `admin` types. Coaches and admins entering others keep ignoring prior knowledge (existing rule).

  *What the youth referee role does today, generalised per qualification:*
  1. **Required duty per age class.** Home games of age classes with `youth_referee` get the referee duty automatically, also without a helper plan or template. Generalise to "required duty types per age class" (age class setting or sport profile), with the youth referee duty as the handball default for the youngest classes.
  2. **List per qualification.** Referees have their own view of the helper plan across all teams (all open referee slots of all games). Generalise: everyone with an `admin` qualification gets a chip/view "<qualification>" in the helper tab with the open slots of that duty type across teams (today `GET /duties/referee`, `REFEREE_TEAM_SQL`, live hub with key 0).
  3. **Children do it themselves.** A qualification can belong to a child; the parent sees it and can sign the child up ("Who referees?"), the child signs up itself if it has an account. Keep the child-permission and age-class child-limit rules.
  4. **Automatic group.** `teams.auto_members = 'referees'` becomes "members are everyone with qualification X" (e.g. `auto_members = 'qualification:<dutyTypeId>'` or a separate column). Leads are managed by hand (see the entry of the same day: admins are no longer added automatically).
  5. **Grant by link.** `referee_links` becomes a link per qualification ("Grant tournament management"), hashed, single or multi use as today; plus switches in the person sheet under "Roles in the club" for every `admin` qualification.
  6. **Notifications.** "Youth referee wanted" (`duty_referee_open`) becomes "<duty type> wanted" for the qualified people; the existing "open slots" logic must respect grants, not only consents (club app: `worker/domain/duty-notify.ts` reads `skill_consents`).

  *Admin UI.* Duty type sheet: "Needs prior knowledge" → choice "Who approves: the person in the profile / an admin". Person sheet: under "Roles in the club" one switch per admin qualification. Profile "What I can do": self qualifications as switches, admin qualifications only as information ("Approved by an admin") when granted.

  *Migration for existing clubs.* `referees` rows → grants of the youth referee duty type (`grant = 'admin'`), `referee_links` → links of that qualification, the auto group switches to the new member rule, `who_referees` on duty types becomes "qualified people"; keep the previous release working (add now, drop the old tables in a later release) and write the upgrade test. Privacy: a qualification is personal data (visible to admins, the person, their parents and coaches when entering duties); add it to `docs/privacy.md` and the export.

  *Club app status.* The original app does the small step now (2026-11-09): duty types with prior knowledge get "approved by an admin", grants per person in a new table, switches in the person sheet, profile shows them read-only, `mayTake` and the open-slot notifications check them; the youth referee role stays as it is there until Kabine has this redesign. A separate entry will describe that change once it is live.

- **2026-11-09 Fix: coach mode only while the admin is a coach somewhere.** An admin in coach mode who lost their last coach role (e.g. removed as lead of the youth referee group) had admin rights suspended but no switch to come back, because the switch is only shown with a coach role. Now `coach_mode` only takes effect while the person has a coach membership: in `loadActor` (`worker/auth/actor.ts`) the query reads `a.coach_mode AND EXISTS (SELECT 1 FROM team_memberships tm WHERE tm.person_id = p.id AND tm.role = 'coach') AS coach_mode`. Test: `test/parent-access-admin-mode.test.ts` ("loses the last coach role in coach mode").
- **2026-11-09 Youth referee group: leads by hand instead of all admins.** The auto group for youth referees made every admin a lead, nightly and on every role change, so an admin could not leave it (and could not get rid of it in coach mode). Now only the members follow the role; leads are added and removed by admins like in any group, existing leads stay, new admins are not added automatically. `syncAutoGroups` (`worker/domain/groups.ts`) no longer touches `role = 'coach'`; `POST /teams/:id/members` and `DELETE /teams/:id/members/:personId` refuse only players (`auto_members`) in auto groups; the group page lets admins manage leads, texts adjusted. Test in `test/groups.test.ts`.
- **2026-11-09 Helper tab: all teams by default, team filter like the events list.** The helper tab always preselected the first team, while the events list shows all teams and filters on tap. Now without a selection the helper tab lists the events of all its teams together (each with its team badge), a tap on a team filters, a second tap clears the filter; the youth referee view is its own list and not part of "all"; top helpers only for a single team. Server: `GET /duties?teamIds=1,2` returns the events of several teams in one answer, an event of several teams only once (`teamDutyGames` in `worker/routes/duties.ts`, `team` is null for several). App: `HelpersPage` (`selected` instead of `teamId`, `LiveReload` per team, only one of them polls every 5 minutes), badge spacing `.team-badge.duty-team`. Tests in `test/duties.test.ts` and e2e.

- **2026-11-08 Fix: the helper plan link on an event opens that team and that event.** The links "Helper plan · …" on the event page (and "Manage helper duties in the Helpers tab") went to the bare helper tab, which always opened the first team, so people did not find the game they came from. Now the link is `/helfer?mannschaft=<teamId>&spiel=<eventId>` (`helperPath` in `src/duties.tsx`: the first team of the event that is in `me.helperTeams`, else the youth referee view `?kihasl&spiel=…` for referees). The helper tab preselects that team (for admins also a team that is not their own, switching the "own/all" filter), scrolls the event into view once the list has loaded and highlights it for 2.5 s (`id="termin-<id>"` on the game article, `.duty-game-target`). Club app: `src/duties.tsx`, `src/pages/event.tsx`, `src/pages/helpers.tsx`, `src/styles.css`; e2e in the helper plan test.
