# Tasks from the original club app

Kabine started as the app of one handball club, which is still developed on its own. New features and bug fixes made there are listed here so they can be brought into Kabine. Whoever works on Kabine takes an open entry, ports it the Kabine way (English source, Lingui, club profile instead of club data, modules, tests) and moves it to "Done" with the Kabine commit.

Entries describe the change, not the club: no names, domains or data of the club.

Format per entry: date, title, what changed and why, where in the code (file and function names are the same in both code bases unless noted), and anything that needs adapting for Kabine.

- **2026-11-19 Server errors: never show the raw error, count per day in KV, email the owner from the third error a day.** Trigger: another project in the same Cloudflare account showed users "D1_ERROR: Your account is generating too much load on D1 DBs. Please back off and try again later." The limit is per account, so the app can hit it as well. `onError` in `worker/app.ts`: unexpected errors never expose their text. Overload (message matches "too much load", "overloaded", "back off", "Network connection lost", "exceeded timeout", "temporarily unavailable", "too many requests") answers 503 `overloaded` with "Things are very busy right now. Please try again in a few minutes."; everything else stays 500 `internal`; `ApiError` is unchanged and not counted. New `worker/lib/server-errors.ts`: `recordServerError(env, where, err)` keeps one KV record per local day (`server-errors:YYYY-MM-DD`, TTL 14 days) with a count and up to 20 entries: UTC time, kind (overload/error), where (route via `routeLabel` with ids and tokens replaced by `:id`/`:token`, or the cron task name), first 300 characters of the message (the cause only when it adds something; D1 repeats the message as cause). After 20 a day it no longer even reads KV, so an error burst cannot use up the KV write quota that login challenges and maintenance mode need. KV instead of D1 because D1 is what fails under overload; no lock, counts are approximate under concurrency. Never throws. From the third error of a day one email (`alertMail`) to the app owner, at most one per day, listing the errors so far; a failed send is retried with the next error; staging logs the mail instead. Called from `onError` (via `executionCtx.waitUntil`), each failing cron task in `handleScheduled`, the job catch in `worker/queue.ts`, the unexpected-error branch of the fixture import (`worker/routes/games.ts`), the holiday import in the season change preview (`worker/routes/season.ts`) and the login mail send (`worker/routes/email.ts`). Tests: `test/server-errors.test.ts`. Kabine: the club app mails a hard-coded owner address (`OWNER_EMAIL` in `worker/auth/owner.ts`); Kabine keeps the owner as a person id in the club profile without an email, so use the owner's verified account email (or admin email) and skip the mail when there is none or no `EMAIL` binding. User-facing texts and the mail go through Lingui.

- **2026-11-13 Polls: choice, scheduling and orders (live in the club app since 2026-11-15). Port to Kabine as a module `modules/polls/`, not into the core.** Coaches ask their team or group, admins the whole club (all teams, no groups). Three kinds: choice (single or multiple answers), scheduling (yes/maybe/no per date, like Doodle) and order (items with price, optional sizes, quantity). Who votes: players (group members), parents (teams with parents only), coaches, combinable; for players in teams with parents the parents also vote for their child, for orders only the parents. Optional "one vote per family": everyone connected through parent links (parents, children, siblings, patchwork) is one unit with a shared, editable ballot ("last changed by …"). Eligible units live in `poll_voters` (unit, member, may vote) and are re-synced hourly while a poll runs, keeping unit ids so ballots survive (`computeVoters`, `syncVoters`, `runPolls` in `worker/domain/polls.ts`; migration `0033_polls.sql`). Votes can be changed and withdrawn until the end. Results "visible now" or "after the end"; creator, team coaches and admins always see them. Names: managers see names and who is missing unless anonymous; participants see names only for non-anonymous scheduling polls, as "First L." (an exception to the names-only-to-coaches rule, documented as a club decision). Anonymous: nobody sees who voted what, the unit is still stored so ballots stay editable and reminders go only to missing voters; orders cannot be anonymous. Orders: the creator (admins as fallback) ticks "paid" per order; no free text. Payment: club-wide setting under admin → polls (admins only), stored in `app_meta` key `poll_payment`: optional PayPal.me name (only paypal.me names; the app opens paypal.me with the family's amount) and/or account holder with IBAN (checksum validated); applies to every order poll. Voters who ordered see amount, PayPal button, IBAN and reference with copy buttons and an EPC QR code (GiroCode, rendered in the app with `uqr`).
